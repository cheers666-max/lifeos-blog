前面三篇（[DPO](../dpo-preference-optimization/)、[IPO](../ipo-identity-preference-optimization/)、[GRPO](../grpo-group-relative-policy-optimization/)）讲的是**方法本身**：损失怎么推、advantage 怎么算。

这篇不一样，讲**把方法用在一个真实项目上时，到底会在哪里卡住**。

项目背景一句话：让模型读用户 query，直接生成一份能渲染的完整 HTML 演示文稿（PPT）。5 类页面——标题、目录、内容、图表、SVG。

先说结论，因为结论比过程有意思：

> **同一批数据、同一个基座、同一套超参，只把 reward 函数从 v3 改到 v4.2，Layout clean rate 从 88.1% 涨到 95.0%（+6.9pp）。**

这个数字不是靠多训几轮、多标几千条数据换来的。是靠**想清楚「什么算好」**换来的。

## 这趟要走的路

1. 先看困局：一个已经饱和的指标，和一堆它看不见的问题；
2. v3 的第一版 reward：数 issue 个数——然后被模型当场教做人；
3. 三个改动：严重度加权、INFO 白名单、issue 分级；
4. 结果 + 一个反直觉的观察：**为什么我没有继续调 reward**；
5. 从这件事里能拿走的三条通用经验。

---

## 1 · 困局：指标满了，问题还在

训练到中段的时候，评测曲线是这样的（就是上面那张图）：绿色是 4 TSV 通过率，橙色是几何干净率。

- **4 TSV 通过率**：90% → 100%（94/94 全部通过），两轮之后彻底贴顶。
- **Layout clean rate**：卡在 **88.1%**，怎么训都不动。

而人工抽查的时候，问题明明白白摆在那儿：

- 两个元素**叠**在一起，文字盖住文字；
- 元素**超出**了 viewport，右边被裁掉半截；
- 字号**小到**在投影上看不清。

这些是用户打开 PPT 第一眼就能看到的问题。但它们**在 4 TSV 里一个字都不体现**——因为 4 TSV 检查的是「结构对不对、能不能渲染」，不是「长得对不对」。

这里就是整件事的关键，值得停下来讲清楚：

> **一个指标饱和了，不是模型学好了，是这个指标再也给不出梯度了。**

在监督学习里这没什么办法，你只能换数据。但在 RL 里你有另一个选项：**换 reward**。

因为 RL 的优化目标不是「拟合标签」，是「最大化 reward」。reward 写的是什么，模型就优化什么。指标饱和只说明**当前 reward 已经吃满了**，不说明模型没空间了。

于是动机非常清楚：**我需要一个「模型正在生成时就能拿到」的、针对几何问题的信号。**

这就是 reward 该出现的位置。

## 2 · v3：数 issue 个数，然后被模型教做人

几何检测服务已经有了——它能把一页 HTML 丢进去,返回一串 issue：

```
{ id: "overlap",        severity: "ERROR"   }
{ id: "element_clipped",severity: "ERROR"   }
{ id: "font_too_small", severity: "INFO"    }
{ id: "offscreen",      severity: "INFO"    }
```

最直觉的写法，也是我第一版写的：

$$
\text{score} = 1 - \text{clip}(\text{issue\_count} \times 0.05,\ 0,\ 0.5)
$$

数一数这页有几个 issue，乘个系数，减掉。**不加权，不分类型，一视同仁。**

跑起来之后，指标确实动了。然后我看了一眼训练日志里的 case，发现了这个：

{{< figure src="02-reward-hack.png" alt="修 1 个元素重叠得 +0.05，修 3 个 INFO 噪声得 +0.15" caption="v3 的致命漏洞：修一个用户看得见的重叠，不如修三个用户根本不在意的噪声" >}}

模型学到的东西是：

> **「减少 issue 的**数量**」**，而不是「解决用户的痛点」。

具体怎么作弊的：把 1 个 `overlap`（用户一眼看见的重叠）留着，转而去消掉 3 个 `offscreen` / 轻微 overlap 这类 INFO 噪声。issue 总数从 4 降到 3，reward 反而更高。**而用户体验没有任何改善。**

这是 reward hacking 的教科书案例。它不是模型坏，是**你给的信号里真的没有「轻重」这个信息**——模型只能猜，猜的结果就是找最便宜的那条路。

> **小结**：reward 写的是「数量」，模型就只优化数量。**下一版要把「轻重」写进信号里。**

## 3 · v4.2：三个改动，把「轻重」写进去

### 改动一：severity 加权

最外层先按检测服务给的严重度分档：

| severity | 权重 |
|---|---|
| ERROR | 1.0 |
| WARNING | 0.7 |
| INFO | 0 |

ERROR 是「必须修，不修就是废品」；WARNING 是「该修」；INFO 默认归零。

### 改动二：INFO 白名单

但 INFO 全归零会误伤。有两类 INFO 是**真实的用户痛点**，只是检测服务把它们定级定低了：

- `text_truncated` —— 文字被截断，用户直接看到省略号
- `font_too_small` —— 字号过小，投影上根本看不清

这两类保留 **0.6** 权重，其余 INFO 一律归零。

这一步的思路值得单独说：**白名单不是「多加一点权重」，是「声明这两类例外」**。前者会让模型继续在噪声里找便宜，后者明确告诉它边界在哪。

### 改动三：issue-id 分级

同一 severity 内部，问题也不是等价的。按修复价值再排一次：

| issue id | 权重 |
|---|---|
| `overlap` / `element_clipped` / `visual_overflow` | 0.10 |
| `zero_size` | 0.08 |
| `text_truncated` | 0.06 |

`overlap`（重叠）、`element_clipped`（被裁）、`visual_overflow`（越界）—— 这三个是「一眼废」级别，给最高。
`zero_size`（元素尺寸为零，等于消失了）次之。
`text_truncated`（截断）再次之。

三档叠起来，最终的权重分布长这样：

### 还有一处工程坑

reward 计算要在训练循环里跑，意味着每一步都要真的渲染页面 + 跑几何检测。而 HTML 里引用了外网 CDN 资源（字体、图标），Playwright 拉不到会一直等到超时——**单页卡死 >120s**。

解法很土但有效：**训练用的渲染环境里把外网 CDN 全部剥离**，本地补上必需的字体。渲染时间从「有时 2 分钟」变成「稳定几百毫秒」。

> 这类坑不会写在论文里，但它是「reward 能不能真的跑起来」的分水岭。**reward 再漂亮，一秒钟算不出来就是零。**

## 4 · 结果，和一个反直觉的决定

三处改动上线，「未换数据、未换基座」：

{{< figure src="04-result.png" alt="clean rate 88.1%→95.0%，难点 case 从 2/7 到 7/7" caption="左边是整体指标，右边是那 7 个历史难点 case——这里的变化比整体数字更有说服力" >}}

- **Layout clean rate：88.1% → 95.0%（+6.9pp）**
- **INFO issue 数量：8 → 1**
- **7 个历史难点 case：2/7 clean → 7/7 clean**

最后这一条我觉得比整体数字重要。整体 +6.9pp 可能来自「简单 case 更稳了」，但**难点 case 从 2 个变 7 个**说明模型真的学会了处理以前处理不了的情况。

### 然后我停手了

按理说，reward 有效，应该继续调——调权重、加项、试更多组合。我没调。

原因是我观察到**reward 开始饱和**了：

- step 7–9 的 score mean 已经到 **0.974–0.995**；
- max 稳定在 1.0；
- min 还有 0.4–0.5（说明还有翻车样本）。

这时候继续调 reward 的收益已经很低了，因为**组内 advantage 的方差在变小**。GRPO 靠「组内平均」算 advantage（[上一篇](../grpo-group-relative-policy-optimization/)讲过），当一组里大部分答案都接近满分时，$\hat{A}_i = (r_i - \text{mean})/\text{std}$ 的分子分母同时在缩，信号变弱。

**继续调 reward 会进入一个假象**：训练 loss 看着在动，评测指标不动。这时候该做的不是继续磨 reward，而是换问题——**或者接受这一版，去解决下一个真问题。**

这条判断我觉得比 +6.9pp 本身更有价值。**知道什么时候停，比知道怎么继续更难。**

## 5 · 三条可以拿走的经验

### 一、reward shaping 的杠杆，远大于堆数据

这是这次最直接的体感。从 v3 到 v4.2，我**一行训练数据都没动**。

- 数据侧：之前试过 6 版数据集演进（10,130 → 9,978 条），做过 OCR 截断修复、SVG 截断修复、CSS 范式统一，甚至做过一次「结构重写」的对照实验——结果**主观质量反而下降**，说明清洗过度会抹平风格多样性。
- reward 侧：三个改动，一天之内，+6.9pp。

原因不难理解：**数据决定「模型见过什么」，reward 决定「模型往哪走」。** 当模型已经见过足够多的样本、但输出方向不对时，加数据是在错误的梯度方向上加燃料。

### 二、模型永远会找最便宜的路，这不是 bug

v3 那个「修 3 个噪声不修 1 个重叠」的行为，第一次看到会很无语。但换个角度：**在 v3 的奖励函数下，那确实是最优解。** 模型做的是完全理性的决策。

所以遇到 reward hacking，第一个反应不该是「模型怎么这么蠢」，而是「**我的 reward 里哪个地方给了它这条路**」。

顺带一提，这也是为什么「单信号学不到」在偏好学习里反复出现。我做过一组 DPO 的对照：**只用留白一个信号，margin 是 −0.016，准确率 22%**（基本等于瞎猜）；**加入 OCR 截断信号后，margin 立刻显著**。单信号的偏好数据里，好坏序根本立不住。

### 三、把问题变成可优化的数，是这件事的全部

回头看，这个项目从头到尾其实只做了一件事：

> **把「排版丑」这个说不清好坏的东西，变成一个能算的数。**

- 4 TSV 能判「能不能渲染」，判不了「好不好看」；
- 几何检测能判「有没有重叠」，判不了「重不重要」；
- **reward 函数的工作，就是补上「重不重要」这一层。**

同样的事我在评测侧也做了一遍：用 Opus 给 30 张 PPT 做七维人工打分当伪标签，去对齐规则 scorer 的权重，把 Pearson 从 **0.34 拉到 0.67（+97%）**。本质是一样的——**让一个便宜但粗糙的指标，尽量贴近人的真实判断。**

## 最后

如果你只记一句话：

> **在 RL 里，指标饱和通常不是终点，是 reward 该重写的信号。而重写 reward 的第一步，是问清楚「用户的痛点，到底哪几个」。**

数据是燃料，reward 是方向盘。燃料再多，方向不对也到不了。
